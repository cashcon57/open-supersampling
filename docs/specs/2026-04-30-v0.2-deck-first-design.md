# ORS v0.2 — Steam-Deck-First Upscaler Design Spec

**Date:** 2026-04-30
**Status:** Draft for review
**Supersedes:** the implicit "v0.2 = Windows DLL drop-in" plan from earlier in goals.md
**Predecessor:** v0.1.0-mvp (PyTorch reference, shipped 2026-04-29)

## 1. Goal

Ship the first ML-quality temporal upscaler that runs well on Steam Deck (RDNA 2, 15W TDP), at internal resolutions as low as 240p outputting to 800p. Quality bar: meaningfully better than FSR 2/3 at extreme upscale ratios; competitive with FSR 2 at moderate ratios; better than NIS / FSR 1 always.

## 2. Why Deck-first

- DLSS doesn't run there. FSR 4 / Ray Regen don't run there (RDNA 4 only). XeSS XMX path doesn't run there. We're competing against bilinear, NIS, FSR 1, and FSR 2 — all beatable.
- ~5M+ Steam Deck units shipped, active modding ecosystem (Decky Loader, gamescope-tools, CryoUtilities).
- Single-platform validation (Linux + Vulkan + RDNA 2) → fast iteration.
- Console proxy: Deck = RDNA 2 = same architecture as PS5 / Xbox Series X.
- gamescope integration provides system-wide upscaling without per-game work.

## 3. Architecture overview

### 3.1 Hardware tiers (4 NN sizes + 1 fallback)

| Tier | Params | Target HW | Quality target | Perf target @ output 800p |
|---|---|---|---|---|
| Spatial fallback (in dispatcher) | 0 (compute shader only) | DX11 / Vulkan 1.0 / Metal 2.0 baseline (~2012+) | beat NIS / FSR 1 via G-buffer-aware edges (when available) | ~0.3-0.5 ms on Deck |
| **ORU-Pico** | **~250-300K** | **Steam Deck (RDNA 2 8 CUs, no WMMA), PS5 / Series S, mobile iGPUs** | **beat FSR 2 at extreme upscale (3-5×)** | **<1 ms on Deck** |
| ORU-Tiny | ~500K | GTX 10/16 series, RX 5000, RDNA 2 desktop, Iris Pro | match FSR 2 at moderate scales | <1.5 ms on GTX 1660 |
| ORU-Lite | ~1M | RTX 20+, RDNA 3+, M-series base, integrated AI accelerators | match DLSS-SR Quality | <1.5 ms RTX 4070 |
| ORU-Standard | ~2.6M | RTX 4080+, RX 9070 XT+, M3 Pro+, full coop_matrix HW | beat DLSS-SR Quality | <2.5 ms RTX 4090 |

ORU-Pico is the v0.2 ship priority. Other tiers train alongside but Deck validation gates the release.

### 3.2 Network architecture (all tiers)

NPPD-derived kernel-prediction U-Net pyramid, two-branch input layout, late fusion. Same shape as v0.1 ORU but tier-scaled and with real training data.

Inputs depend on integration path (see §4):

- **Image-only path (gamescope)**: low-res RGB, motion-vector estimate from frame-difference, history (warped prior denoised output)
- **G-buffer path (DLL swap)**: low-res RGB, depth, true motion vectors, jitter pattern, history

The network internally always consumes a fixed-shape feature tensor; the per-path adapter normalizes inputs to that shape. Same trained weights work for both paths — the adapter is a 2-layer ConvBlock that maps available signals into the canonical feature tensor.

### 3.3 Channel widths per tier

Multiples of 8 throughout for cooperative-matrix tiling compatibility.

| Tier | Stage 0 | Stage 1 | Stage 2 | Stage 3 | KPN kernel |
|---|---|---|---|---|---|
| ORU-Pico | 16 | 24 | 32 | 40 | 5×5 |
| ORU-Tiny | 16 | 24 | 32 | 48 | 5×5 |
| ORU-Lite | 24 | 32 | 48 | 64 | 5×5 |
| ORU-Standard | 32 | 48 | 64 | 96 | 7×7 |

## 4. Integration paths

Two paths shipped together. Dispatcher picks the best available at runtime.

### 4.1 Path A — gamescope plugin (image-only, universal coverage)

- Built as gamescope-loadable filter alongside FSR 1 / NIS / Lanczos
- Receives final composited RGB frame from any game
- Estimates motion vectors via cheap frame-difference + optical-flow heuristic (1 pass, ~0.1 ms on Deck)
- Maintains internal 1-2 frame history buffer
- Outputs upscaled RGB to display
- Quality ceiling: **better than FSR 1 always; better than FSR 2 at 4×+ scales because FSR 2 itself breaks down with sub-pixel motion at 240p input**
- Coverage: every game on Deck system-wide, no per-game work

### 4.2 Path B — DLL swap (full G-buffer access, higher quality)

- Linux `.so` + Windows `.dll` builds
- Implements NGX SR API surface (DLSS-SR replacement) + FidelityFX API surface (FSR replacement) + XeSS API surface
- OptiScaler is the engineering reference for hooking pattern + signature spoofing
- Receives full input contract from games that ship FSR 2/3 / DLSS-SR / XeSS DLL: depth, motion vectors, jitter, history
- Quality ceiling: **FSR 2/3-class with our trained weights; meaningfully better at extreme scales**
- Coverage: games that ship one of the three DLL APIs

### 4.3 Dispatcher logic

At runtime, ORS picks the best available path per game:

1. Game ships a swappable DLL (DLSS / FSR / XeSS) → **Path B** (full G-buffer)
2. Otherwise gamescope plugin is loaded → **Path A** (image-only)
3. Otherwise hardware can't run NN → spatial fallback shader (compute-only)

User typically gets Path B in modern AAA, Path A in older/indie/Linux-native games.

### 4.4 Vulkan layer — explicitly out of scope

Considered and rejected. Games that render at extreme low res essentially always ship an FSR/DLSS/XeSS DLL (that's why they can render so low). Games without those DLLs render at native and don't need our temporal pipeline. The Vulkan-layer engineering investment doesn't pay off at v0.2 scale. Possibly revisited in v0.4 if a real demand signal emerges.

## 5. Inference engine

### 5.1 Backends

| Backend | Platform | Status in v0.2 |
|---|---|---|
| Vulkan compute (SPIR-V from HLSL via DXC, or GLSL) | Linux (Deck), Windows, Apple via MoltenVK | **primary** |
| ONNX Runtime + DirectML | Windows | secondary, dev-time validation |
| ONNX Runtime + CoreML / MPSGraph | macOS dev box | dev-time validation |
| Metal compute (MSL `simdgroup_matrix`) | Apple Silicon | v0.3 (deferred from v0.2) |
| HLSL Cooperative Vectors (DX12 SM 6.9) | Windows DX12 | v0.3 perf push |

Vulkan compute is the v0.2 primary because it covers Deck (the priority target) and Linux desktop and Windows via the same SPIR-V binary.

### 5.2 Quantization

| Tier | Training precision | Inference precision (Deck/desktop) |
|---|---|---|
| ORU-Pico | FP16 | FP16 packed (RDNA 2) |
| ORU-Tiny | FP16 | FP16 packed |
| ORU-Lite | FP16 | FP16 + INT8 weight quant where supported |
| ORU-Standard | FP16 | FP8 on RDNA 4 / Blackwell where available; FP16 fallback |

INT4 / FP8 not used for ORU-Pico — the constraining tier (RDNA 2) doesn't have those paths.

## 6. Training pipeline

### 6.1 Datasets

**v0.2 dataset target: ~30K paired (low-res input + GT high-res) sequences** drawn from:

1. **Mitsuba 3 rendered scenes** (Bistro + Sponza + Bitterli benchmark + Blendswap CC0/BY) at 800p reference, downsampled to 240p/360p/540p targets via box filter. Real motion vectors derived from `position` AOV + per-frame view-projection matrix. ~$200 cloud render budget on A6000 / 4090 Lambda instance.
2. **Real game frame captures** via RenderDoc/PIX traces from Deck-popular titles (Hades II, Helldivers 2 if available, Cyberpunk raster, Stardew Valley, etc.). Motion vectors + depth captured live. ~$0 — runs locally on RTX 3080 Ti or via Wine on macOS.
3. **Procedural augmentation** of Mitsuba scenes (KPCN-style: ~8 base scenes × random material/HDRI/camera permutation → ~1500 sequences).

Dataset license whitelist enforced: Bitterli, Bistro (CC-BY 4.0), Sponza (CC-BY 3.0), Blendswap CC0/BY only. **No Quixel, Megascans, Moana, or CC-BY-NC-* assets.**

### 6.2 Training compute (Lambda)

| Task | Instance | Hours | Estimated cost |
|---|---|---|---|
| Mitsuba dataset rendering | 1× A6000 48GB | ~50-100 | $50-100 |
| Iteration runs (small variants, ablations) | 1× A100 40GB | ~20-40 | $25-50 |
| Final ORU-Pico training | 1× H100 80GB PCIe | ~2-3 | ~$10 |
| Final ORU-Tiny training | 1× A100 40GB | ~3-4 | ~$5 |
| Final ORU-Lite training | 1× A100 80GB | ~4-5 | ~$10 |
| Final ORU-Standard training | 1× H100 80GB | ~3-5 | ~$15 |
| Adapter (image-only ↔ G-buffer) retrain | 1× A100 40GB | ~1-2 | ~$3 |

**v0.2 total Lambda budget estimate: $120-200.** Reserve $1500 as overall headroom; median spend should be far less.

### 6.3 Loss

Composite: relative L2 (HDR-aware, Vogels 2018 / OIDN-style) + 0.1 × (1 - SSIM) + 0.05 × LPIPS-VGG.

Specific to upscaling: also add temporal consistency term — penalize per-pixel difference across consecutive frames after motion-vector reprojection.

## 7. Build + distribution

### 7.1 Build artifacts

| Artifact | Platform | Format |
|---|---|---|
| `liboru-gamescope.so` | Linux (Deck primary, desktop secondary) | gamescope-loadable plugin shared library |
| `liboru.so` | Linux | DLL-swap shared library; symlinks: `nvngx_dlss.so`, `amd_fidelityfx_vk.so`, `libxess.so` |
| `oru.dll` | Windows | DLL-swap library; renamed to match game's expected DLL filename |
| ORU-Pico/Tiny/Lite/Standard weight files | all | ONNX + raw SPIR-V-embedded weight binaries |
| `ors-decky` | SteamOS | Decky Loader plugin packaging the gamescope filter |

### 7.2 Distribution channels

1. **GitHub Releases**: signed tarballs for `.so` / `.dll` / weights / decky package
2. **Decky Loader store** submission for the SteamOS plugin
3. **Flatpak** for desktop Linux distribution
4. **Optional**: AUR / pacman package for Arch / SteamOS-derived

### 7.3 Per-game compatibility

Single shipped JSON profile file: `compat-profiles.json`. Each entry:

```json
{
  "game-id": "cyberpunk2077",
  "exe-name": "Cyberpunk2077.exe",
  "preferred-path": "B",
  "dll-target": "nvngx_dlss.dll",
  "input-quirks": {"motion-vector-space": "uv", "jitter-applied-by-game": true},
  "tier-override": null
}
```

Community-maintainable. Starts with manual entries for ~10 popular Deck games at v0.2 ship; grows over time.

## 8. Test / QA matrix

| Hardware | Role |
|---|---|
| Steam Deck (LCD or OLED, both ideal) | primary target — must run real-time at 800p |
| RTX 3080 Ti via Tailscale | Ampere reference for Tiny/Lite/Standard tiers, DLL swap testing on Windows |
| macOS arm64 dev box | model dev, ONNX validation, simdgroup_matrix path scoping (deferred to v0.3) |
| Lambda H100/A100/A6000 | training + dataset rendering |
| CachyOS Docker container | Linux desktop validation, gamescope plugin testing without Deck hardware |

### 8.1 First integration tests

Pick 2-3 games installed on the test boxes:

- One modern AAA shipping FSR 2/3 (DLL swap path validation)
- One indie / older title without FSR (gamescope path validation)
- One title where Deck thermal-throttles aggressively (perf-budget validation)

User holds the game library; final picks gated on what's already installed and Deck-popular.

### 8.2 Quality regression baselines

| Comparison | Metric | Threshold |
|---|---|---|
| vs native (no upscale) | LPIPS, PSNR | informational |
| vs gamescope FSR 1 | PSNR, SSIM, LPIPS | ORS must beat by ≥0.5 dB PSNR at all scales |
| vs FSR 2/3 in-game | PSNR, SSIM, LPIPS, temporal stability | ORS must match at moderate scales (1.5-2×); beat at extreme scales (3-5×) |
| vs FSR 4 (where available) | PSNR, SSIM, LPIPS | informational; we don't ship to RDNA 4 only |
| Power draw on Deck | watts at 30/60 fps cap | ORS must not exceed FSR 2 baseline |

## 9. Out of scope for v0.2

- ORD denoiser DLL ship (deferred to v0.3)
- DLSS Ray Reconstruction (`nvngx_dlssd.dll`) replacement (v0.3)
- FSR Ray Regen replacement (v0.3)
- Per-game LoRA adapter framework (v0.3)
- Tile-gated variable-rate inference (v0.3)
- Adaptive sampling (Bálint 2026 paradigm) (v0.5+)
- Frame extrapolation / GFFE-style frame gen (sister project, v0.5+)
- UE5 plugin (v0.4)
- Vulkan validation layer for arbitrary games (v0.4 if demand emerges)
- Apple Silicon Metal compute path (v0.3)
- Console partnerships (v1.0+)

## 10. Risks + mitigations

1. **ORU-Pico can't fit in Deck thermal budget at all output resolutions.** Mitigation: spatial fallback always available as the floor; aggressive distillation if needed. Train with explicit per-pixel-FLOP regularization.
2. **gamescope plugin causes input lag / vsync issues.** Mitigation: gamescope already ships FSR 1 plugin; same framework works for our pass. Test with Deck-stock gamescope build.
3. **DLL swap breaks anti-cheat in some games.** Mitigation: well-documented from OptiScaler. Maintain a per-game "do not run" list. Document for users in compat profile.
4. **Real motion vectors on Deck via DXVK have edge cases.** Mitigation: gamescope path is always the fallback. Document games where DLL swap glitches.
5. **Image-only path quality at 4× scales doesn't actually beat FSR 2.** Mitigation: image-only NN is the floor; if it underperforms, we still beat FSR 1. Marketing claim adjusts but project ships.
6. **License contamination from Quixel / Epic / Moana assets** in real-game-trace captures. Mitigation: only capture from games with materials we can identify as non-restricted; never use captured frames as direct training labels — use them as input distribution for synthetic GT generation.

## 11. Success criteria

v0.2-alpha ships when:

- ORU-Pico runs at <1 ms upscaling 540p → 800p on Steam Deck OLED
- gamescope plugin demonstrates higher quality than gamescope FSR 1 in side-by-side video on a real Deck
- DLL swap path successfully replaces FSR 2 in at least one shipping game with no visible regressions
- Spatial fallback runs on hardware too weak for ORU-Pico
- Public release on GitHub with weights, source, and reproducibility docs

## 12. Open questions (pre-spec-lock)

1. Exact gamescope plugin API — does it accept arbitrary shader stages or only specific filter types? (Read gamescope source.)
2. Do we ship the gamescope plugin as a fork of gamescope or as a runtime-loadable plugin? (gamescope's plugin API is limited as of late 2025.)
3. Does Decky Loader allow shipping a binary `.so`, or only Python plugins? (Affects packaging.)
4. Which 2-3 first integration test games? (Gated on user's installed library + Deck popularity.)
5. Spatial fallback shader — write in HLSL via DXC and cross-compile to SPIR-V, or write GLSL directly? (DXC simpler for toolchain consistency with later Windows ship; GLSL more native for Linux-first.)

Each open question is non-blocking for spec lock; resolves during implementation.
