# Open Reconstruction Suite — Design Spec

**Project name:** Open Reconstruction Suite (ORS)
**Components:** ORD (Open Ray Denoiser), ORU (Open Ray Upscaler)
**Date:** 2026-04-29
**Status:** Draft for review
**License (intended):** Apache-2.0 for SDK and shaders, MIT for engine plugins, model weights CC-BY-4.0

## 1. Goal

A vendor-agnostic, open-source, real-time ray-tracing reconstruction stack. Two independently usable components — ORD (denoiser) and ORU (upscaler) — that together approach DLSS Ray Reconstruction quality and performance via a coordinated feature-handoff pairing, while remaining fully interchangeable with any third-party denoiser or upscaler.

## 2. Constraints

1. **Real-time on any GPU that supports hardware ray tracing.** Min spec: NV Turing+, AMD RDNA2+, Intel Arc Alchemist+, Apple M3+, plus consoles (PS5 / Xbox Series S/X — both RDNA2). No benefit targeted for non-RT GPUs.
2. **Net-positive perf.** Frame using ORS components must be faster than the same frame using a vendor hand-tuned stack at equal-or-better quality. Quality ≥ NRD/FidelityFX denoiser + TSR/FSR baseline.
3. **Vendor-agnostic.** Single algorithm, single set of weights per component, runs on every target. Cross-vendor perf tax acceptable up to ~2× of vendor-tuned reference.
4. **Component-agnostic.** ORD outputs are usable by any third-party upscaler (DLSS-SR, FSR, XeSS, TSR, Arm ASR, MetalFX, off). ORU inputs accept output from any third-party denoiser (NRD, FidelityFX, hand-tuned) or no denoiser. Each component must work standalone.
5. **Open everything.** Apache-2.0 / MIT shaders + SDK. CC-BY weights. Reproducible training pipeline. No proprietary blobs in the ship path.
6. **Permissive enough to ship.** No GPL on shaders (would block AAA console use). GPL-3 acceptable for engine integration plugins.

## 3. Three operating configurations

| Config | Denoiser | Upscaler | Render res | Perf vs DLSS RR | Quality vs DLSS RR |
|---|---|---|---|---|---|
| ORD only | ORD | DLSS / FSR / XeSS / TSR / off | native | matches RR perf only if user is already using DLSS-SR | ~85–90% |
| ORU only | NRD / FidelityFX / hand-tuned | ORU | low | matches FSR/XeSS perf | upscaler-class |
| **Paired (ORD+ORU)** | ORD | ORU | low | **near 1:1 with RR** (joint architecture, low-res render) | **~92–95%** |

Each row is a real shipping configuration. Paired mode is what gets ORS to RR-class numbers; standalone modes preserve the freedom users actually want.

## 4. Pipeline placement

### 4.1 Standalone ORD (denoiser-only)

```
[ Geometry / G-buffer pass ]
        |
        v
[ RT lighting at native res — 1 spp ]
        |
        v
[ ORD ]
   in:  noisy radiance (per signal),
        G-buffer (normals, depth, albedo, roughness, motion vectors),
        prior frame's denoised output + history confidence
   out: clean RGB radiance per signal at native render resolution
        |
        v
[ Lighting compose / tonemap ]
        |
        v
[ Any upscaler — TSR / DLSS-SR / FSR / XeSS / Arm ASR / MetalFX / off ]
        |
        v
[ Display ]
```

### 4.2 Standalone ORU (upscaler-only)

```
[ Game frame at low res — already denoised ]
        |
        v
[ ORU ]
   in:  RGB color, depth, motion vectors, jitter pattern
   out: high-res image
        |
        v
[ Display ]
```

Same input contract as FSR/XeSS. Drop-in replacement.

### 4.3 Paired (ORD+ORU)

```
[ Geometry / G-buffer pass at LOW res ]
        |
        v
[ RT lighting at LOW res — 1 spp ]
        |
        v
[ ORD ] -- emits both:
   * RGB radiance at low res (standalone-compatible)
   * feature tensor at low res (paired handoff)
        |
        +------- feature handoff path -------+
        v                                    v
[ Tonemap (low res) ]              [ ORU paired-input head ]
        v                                    v
[ Composed low-res frame ]         [ ORU temporal+upsample stages ]
        \                                    /
         \                                  /
          ----> [ ORU consumes ] <---------
                       |
                       v
        [ High-res clean image ]
                       |
                       v
                   [ Display ]
```

The paired path delivers the joint denoise+upscale architecture (the RR perf win) while preserving the standalone modes.

## 5. Architecture

### 5.1 ORD (denoiser)

Synthesis of three open primitives:

1. **NPPD-style kernel-prediction U-Net pyramid** (Bálint et al., SIGGRAPH 2023, MIT-style code+weights). Predicts per-pixel filter kernels at multiple scales, partitioning radiance across pyramid levels. Beats KPN/SVGF on ringing and disocclusion. Used as algorithmic baseline by DLSS 4 RR's own paper.
2. **MUNet-style two-branch input layout** (AMD I3D 2025). Separate branches for noisy radiance and noise-free aux buffers (albedo / normal / roughness / depth / specular hit distance), late-fused. Improves edge preservation at low spp. Paper public, weights closed — re-implemented from scratch.
3. **External SVGF-style temporal reprojection upstream** of the network (Schied 2017 / 2018). Motion-vector warp + variance-weighted history blend feeding a feed-forward network. Avoids RNN state cost. ANF (Işık 2021) "running average with learned per-pixel weights" is the proven sweet spot.

**Output mode:** kernel prediction (not direct color regression). Cross-vendor friendly, FP16-friendly, INT8-quantizable, smaller params for equal quality.

**Two outputs per frame:**
- RGB radiance (for standalone use)
- Feature tensor at U-Net penultimate layer (for paired handoff to ORU)

### 5.2 ORU (upscaler)

Temporal supersampling network. Reference architecture: Thomas/Liktor HPG 2022 shared-encoder + multi-scale kernel-prediction reconstruction, scaled down to MVP-budget channel widths.

**Three input modes selected at init:**
- RGB-only (FSR/XeSS-equivalent contract): color + depth + motion vectors + jitter
- RGB+aux (use G-buffer if available): adds normals, roughness for sharper edges
- Feature-handoff (paired with ORD): consumes ORD's penultimate feature tensor directly, skipping a redundant encode/decode cycle

**Standalone competitive against** FSR 2/3/4, XeSS 2, TSR. Upscale ratios: 1.3× / 1.5× / 1.7× / 2.0× per axis (Quality / Balanced / Performance / Ultra-Performance).

### 5.3 Feature handoff contract (load-bearing decision)

The paired-mode interface is defined explicitly in v0.1 and frozen as a public API even though both networks will iterate beneath it.

**Tensor specification:**
- Shape: `[B, C_feat, H_low, W_low]` where `C_feat = 32` for v0.1, reservable to 16/64 in future
- Dtype: FP16
- Spatial layout: same coordinate frame as the ORD input radiance (same jitter, same motion vectors)
- Semantic: penultimate-layer features of ORD's kernel-prediction head before the final RGB projection
- Optional auxiliary tensor: per-pixel confidence map `[B, 1, H_low, W_low]` FP16

**Stability promise:** any ORD version that emits this tensor pairs with any ORU version that consumes it. Both networks may evolve; the contract may not.

**ORU's paired-input head** is a small adapter (~3 conv layers) that maps the feature tensor into ORU's encoder, replacing the standalone RGB encoder for that frame. Adapter is trained separately when ORD's feature distribution shifts.

### 5.4 Model size budget

Targeting the constraining tier (RDNA2 / PS5 / Series X = FP16 only, no matrix accel, ~10 TFLOPs FP16). **Tiered weight sets** per the earlier scope-amendment analysis — same input/output contract, different model capacity:

| Tier | Hardware | ORD params | ORU params | Frame budget @ 1080p in / 4K out |
|---|---|---|---|---|
| Lite | RDNA2 / PS5 / Series X | ≤ 200K | ≤ 300K | < 3.5 ms total |
| Standard | NV Turing+, AMD RDNA3+, Arc, M3+ | ≤ 1M | ≤ 1.5M | < 2 ms total |
| Heavy | RTX 4070+, RX 9000+, M4 Pro+ | ≤ 4M | ≤ 4M | < 1.2 ms total |

Heavy tier may include attention layers; Lite tier is GEMM-only kernel-prediction.

### 5.5 Cross-vendor inference

**Primary path: inline compute-shader GEMM via subgroup matrix instructions.** No ML runtime in the hot path.

| Backend | IR / Extension | Tier coverage |
|---|---|---|
| Vulkan | SPIR-V `OpCooperativeMatrix*` (KHR, 2023) | NV Turing+, AMD RDNA3+, Intel Arc, partial RDNA2 |
| D3D12 | HLSL Cooperative Vectors (SM 6.9 preview, AMD/NV/Intel committed) | All DX12 RT-capable GPUs |
| Metal | MSL `simdgroup_matrix_multiply` | M3+ |
| Fallback | Plain FP16 compute, DP4a where present | RDNA2 PS5 / Series X (no matrix accel) |

**Bring-up / Windows fallback:** ONNX Runtime + DirectML for early development and pre-coop_matrix hardware. Drop ORT once inline path is shippable.

**Forbidden:** tiny-cuda-nn (CUDA-only), CUDA-only EPs, vendor-tuned tensor-core-only kernels in the ship path.

## 6. Open base components

| Component | Source | License | Role |
|---|---|---|---|
| ORD backbone | NPPD (github.com/balintio/nppd) | MIT-style | kernel-prediction architecture starting point |
| ORU backbone | Thomas/Liktor HPG 2022 architecture, re-implemented from paper | derivative work | shared-encoder temporal upscaler |
| Training infrastructure | OIDN training toolkit | Apache-2.0 | end-to-end pipeline scaffold |
| Pre-train init (ORD) | OIDN weights | Apache-2.0 | warm start (3–5× render cost reduction) |
| Pre-train init (ORU) | TSR / FSR open ref or train from scratch | TBD | warm start |
| Spatial / temporal pre-filter | Falcor SVGF + ReSTIR shader code | BSD-3 | upstream variance reduction for ORD |
| World-space cache (v0.1+) | NVIDIA RTXGI 2.0 (NRC v2) | MIT | source-side variance reduction |
| Reference path tracer | Mitsuba 3 (CUDA JIT) | BSD-3 | training data generation |
| Cross-vendor reference | Intel XeSS SDK | MIT | HLSL cross-vendor inference patterns |

**Forbidden bases:** NVIDIA NRD (proprietary RTX SDK SLA), DLSS plugin (closed), Streamline (vendor-coupled), Unreal/Unity bespoke denoisers (engine-EULA only), tiny-cuda-nn (CUDA-only), Quixel/Megascans (UE EULA bars AI training).

## 7. Training data

**Asset whitelist:**
- Bitterli Rendering Resources (32 scenes, public domain / CC-BY)
- NVIDIA ORCA Lumberyard Bistro (CC-BY 4.0)
- Crytek Sponza variants (CC-BY 3.0)
- Blendswap CC0 / CC-BY artists, hand-curated
- Procedural augmentation (KPCN-style: 8 base scenes → 1,484 by material/HDRI/camera permutation)

**Asset blacklist (license landmines):**
- Quixel Megascans / Epic Marketplace — UE EULA forbids AI training
- Disney Moana — research-only license incompatible with shipped permissive model
- ORCA Emerald Square / Sun Temple — CC-BY-NC-SA viral
- Anything CC-BY-NC-* or *-ND

**v0.1 dataset target:** ~10–20K matched pairs (1 spp + G-buffer + 4–8K spp reference). Render with Mitsuba 3 GPU.

**Compute estimate:**
- Reference rendering: 300–1500 GPU-hours (~$200–$1500 on rental, 4090-class)
- Training (ORD): 5–15 GPU-days (~$50–$400)
- Training (ORU): 5–10 GPU-days (~$50–$300)
- Paired adapter retrain: ~2 GPU-days (~$20–$100)
- Total v0.1 training cost: **~$1000–$3000**

**Bootstrapping:**
- Initialize from OIDN weights (Apache-2.0) → cuts render cost 3–5×
- Apply Noise2Noise / Nonlinear-N2N — train from noisy pairs, halve reference-spp budget
- Use diffusion teacher (arXiv 2404.00491) for OOD distillation in v0.2

## 8. Engine integrations

Tiered roadmap. Each is its own follow-on spec.

| Tier | Engine | Hook | Effort | Audience |
|---|---|---|---|---|
| 1 | Path tracer reference (Mitsuba 3 / Falcor) | Direct API | Small | Developer / film / research |
| 2 | UE5 path tracer (`IPathTracingDenoiser` for ORD + `ITemporalUpscaler` for ORU) | Plugin module | Small | Film / archviz / cinematic |
| 3 | UE5 legacy HWRT (`GScreenSpaceDenoiser` swap) | Plugin module | Medium | Custom RT pipelines, deprecated by 5.5+ |
| 4 | Godot 4 RT | Renderer extension | Medium | Indie / open-source community |
| 5 | bevy / wgpu | Crate | Medium | Rust / experimental |
| 6 | UE5 Lumen replacement | Engine fork (NvRTX-style) | Large | Long-term, AAA |
| 7 | Custom integrations (id Tech / Snowdrop / Decima / etc.) | Per-engine | Large | Studio partnerships |

**v0.1 scope: tier 1 only** (reference renderer integration). Tier 2 (UE path tracer for both ORD + ORU) at v0.2. Tier 3+ deferred.

UE EULA explicitly permits permissive plugin distribution — Arm ASR (Apache 2.0) and FidelityFX (MIT) prove the pattern.

## 10. Roadmap (12-month)

- **v0.1 (months 0–4):** ORD + ORU + paired feature-handoff adapter. Vulkan inline-shader inference (Linux/NV proves out the algorithm). Mitsuba 3 reference integration. Initial training corpus rendered. First weights for all three modes (ORD-only, ORU-only, paired). Bench numbers vs DLSS RR / FSR / XeSS / NRD. **MVP target.**
- **v0.2 (months 4–7):** Cross-vendor backend coverage (DX12 + Metal). AMD/Intel/Apple validation. UE5 path-tracer plugin. NRC v2 upstream integration. First public release.
- **v0.3 (months 7–10):** Quality push. ReSTIR PT enhanced upstream. Diffusion-distilled training. Larger dataset. UE5 HWRT plugin. Heavy tier weights.
- **v0.4 (months 10–12):** Production hardening. Godot/bevy plugins. Per-engine tuning guides. v1.0 candidate.

## 11. Comparison to existing closed solutions

| Property | DLSS RR + DLSS-SR | FSR Ray Regen + FSR | NRD + TSR | **ORS (this spec)** |
|---|---|---|---|---|
| Vendor | NV only | RDNA4 only | NV-tuned, console-OK | All RT GPUs |
| Joint denoise+upscale | Yes (single net) | Yes (RR + FSR coupled) | No | **Yes when paired**, optional otherwise |
| License (denoiser) | Proprietary | MIT shell, closed weights | RTX SDK SLA | Apache-2.0 + MIT |
| License (upscaler) | Proprietary | MIT shell, closed weights | UE proprietary | Apache-2.0 + MIT |
| Open weights | No | No | N/A | **Yes** |
| Open training pipeline | No | No | N/A | **Yes** |
| Min spec | RTX 20+ | RX 9000 | RTX 20+ | Any RT GPU |
| Cross-engine | NV-blessed | AMD-blessed | License-gated | All open-source pattern |
| Realistic perf delta vs RR | 1× (reference) | ~1.1× | ~1× | ~1.05–1.3× paired, ~1.5–1.8× ORD-only |
| Realistic quality delta vs RR | 1× (reference) | ~0.9× | ~0.85× | ~0.92–0.95% paired, ~0.85–0.9% ORD-only at 12 mo |

Gap to DLSS RR is **engineering + training data + integration**, not research.

## 12. Risks and open questions

1. **OIDN 3 (H2 2026) ships temporal denoising** with kernel prediction. **Mitigation:** position ORS as the cross-vendor *real-time* layer OIDN won't be (OIDN targets interactive/offline). Coexistence rather than competition.
2. **AMD FSR Ray Regen** may go cross-vendor. Same mitigation: FSR-RR is joint-but-FSR-coupled; ORS pairs with itself or anything else.
3. **HLSL Cooperative Vectors final spec** (SM 6.10) may diverge from preview. **Mitigation:** primary path is SPIR-V coop_matrix (stable since 2023).
4. **RDNA2 / PS5 / Series X budget tightness** at Lite tier. **Mitigation:** Lite tier ships smaller model; document quality tradeoff honestly.
5. **Training data licensing** is the most fragile area. **Mitigation:** strict whitelist enforcement.
6. **Lumen integration story is bad on vanilla UE.** **Mitigation:** target path-tracer denoiser slot first; engine-fork for v0.4+ if there's pull.
7. **Feature handoff contract** is load-bearing — wrong shape locks both products. **Mitigation:** ablate aggressively in v0.1 MVP, freeze only after empirical validation.
8. **ORU launches into a competitive field (FSR/XeSS/TSR all moving fast).** **Mitigation:** the open-weights + community-governance differentiator is real and durable.
