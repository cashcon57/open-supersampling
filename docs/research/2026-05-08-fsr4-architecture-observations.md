# FSR 4 Architecture Observations — for OSS v6.2 Student Design

**Date:** 2026-05-08
**Source:** AMD FidelityFX SDK 2.0.0 at orphan commit `01446e6a` (MIT-licensed; vendored at `oss/third_party/fidelityfx-sdk-2.0.0-mit/`).
**Purpose:** Identify architectural elements worth borrowing for the v6.2 student model (independent reimplementation, not direct port). MIT terms permit direct port too, but for v6.2 we want OSS architecture to remain visibly distinct — borrow building blocks, not topology.

---

## TL;DR — what to borrow

| Element | Borrow for v6.2? | Notes |
|---|:-:|---|
| **FasterNet block** (concat shortcut + 3×3 PW conv + 1×1 conv + activation) | **Yes** | Public technique (Chen et al. CVPR 2023); FSR 4 uses 48-feature variant, no group split. Strong fit for OSS student backbone |
| **SqrSwish activation** (softsign-Swish) | **Yes** | `0.5·v·(1 + v/√(v²+1))`; cheaper than Swish (no exp), FP16-friendly, bounded gradient |
| **Fused mega-kernels** (Conv3p1b → Conv1b → SqrSwish → Conv1b → Add → Add → ConvTranspose2D) | **Pattern, not ports** | Validates kernel-fusion strategy; we design our own fusions for the canvas-residual pipeline |
| **FP16 NHWC layout + INT8 weights with DequantizeLinear** | **Yes** | Production-tested quantization recipe; matches our v6.2 hardware-tier matrix |
| **Edge padding via "skip if !ValidPosition"** (no zero-pad, no border-replicate) | **Yes** | Performance optimization that AMD validated as visually invisible in games |
| **2:1 resize via ConvTranspose2D_k2s2b** at output | **Maybe** | Standard for ML upscalers; fits our Performance tier |
| **Whole-frame ML upscaler topology** | **NO** | This is the differentiation point. OSS keeps canvas-residual; FSR 4-style topology is what we're explicitly NOT |
| **Frame extrapolation as a separate pipeline** | **NO** | OSS structural advantage: canvas warp = free FG. FSR 4 ships frame-gen as a separate DLL |
| **Compute Shader 6.4 hardware floor** | Partial — we target broader | We support down to no-ML shader path; FSR 4 needs RDNA 4 INT8 matrix engines |

## What FSR 4 is, structurally

Reading `Kits/FidelityFX/upscalers/fsr4/dx12/`:

- **Dispatch surface:** `ffx_provider_fsr4_dx12.cpp` (host C++) configures + binds resources, then dispatches a sequence of compute kernels generated by AMD's "ml2code" PyTorch→HLSL transpiler
- **Kernel library:** `ml2code_runtime/operators/float16_NHWC/` is the production path; `ml2code_runtime/operators/float32/` is the slow-path fallback
- **Quantization:** weights are INT8, decoded at load time via `DequantizeLinear.hlsli` to FP16 for compute
- **Layout:** NHWC (channels-last) — different from PyTorch default NCHW. Cache-friendly for per-pixel patterns where adjacent threads access adjacent channels
- **Build process:** `BuildFSR4UpscalerShaders.bat` compiles the HLSL, `BuildFSR4Initializers.bat` packs the INT8 weights into the shipping binary
- **Public API surface:** `Kits/FidelityFX/upscalers/fsr4/include/ffx_fsr4upscaler.h` — context creation, frame description struct, dispatch entry point

Forward graph (inferred from operator names; AMD has not published the exact topology in source comments):

1. **Stem:** `Conv2D_k3p1b` (3×3 with padding, with bias) — feature extraction from LR + reprojected previous frame
2. **Body:** several `FasterNet48_NoGroup` blocks — the bulk of the compute. Each FasterNet block is:
   - Concat (channels) of input + skip path
   - 3×3 pointwise conv (16 features)
   - 1×1 conv (with bias)
   - SqrSwish
   - 1×1 conv
   - Add (residual)
3. **Mega-fused blocks:** `FusedConv2D_k3p1b_Conv2D_k1b_SqrSwish_Conv2D_k1b_Add_Add` and the `_CT2D` variant — single kernels combining 4-7 operations to minimize intermediate memory traffic
4. **Upsample:** `ConvTranspose2D_k2s2b` — 2× spatial upsampling (input is at LR, output at HR after 2 of these for 4× total)
5. **Tail:** final `Conv2D` to RGB output

Total parameter count is not exposed in source. Public AMD claim is "13M params for the FSR 4 model" (per various press releases referencing AMD's GDC talks). Inference runs at ~1.5-2.5ms on RDNA 4 at 1440p→4K per public benchmarks.

## SqrSwish — why it's interesting

Definition (from `scalar_functions.hlsli:27`):

```hlsl
template<typename T>
T SqrSwish(const T v) {
    return 0.5 * v * (1. + v / sqrt(v * v + 1.));
}
```

This is **NOT** what the name suggests. It's not "squared Swish" (`(x · sigmoid(x))²`). It's a **softsign-based Swish variant**:

- `softsign(x) = x / (1 + |x|)` — well-known, but NOT what FSR 4 uses
- AMD uses `x / √(x² + 1)` which is a smooth approximation of `sign(x)` — call this "smooth-sign" — and forms `0.5·x·(1 + smooth-sign(x))`
- Result is a Swish-shaped curve: monotonic, smooth, bounded gradient, preserves sign of input

**Why it's better than `x · sigmoid(x)` for inference:**

| Property | Swish (`x · σ(x)`) | SqrSwish |
|---|---|---|
| Compute | `1/(1+exp(-x))` — needs exp | `1/√(x²+1)` — needs only mul, add, sqrt, div |
| FP16 numerics | exp can over/underflow on FP16 narrow range | sqrt + div is well-conditioned in FP16 |
| GPU throughput | exp is ~1/4 rate of FMA on Ada/Ampere | sqrt is ~1 rate (or fast intrinsic) |
| Gradient | Bounded but exp-shaped tail | Bounded with smoother saturation |

**v6.2 candidate:** swap GELU (current) for SqrSwish in the student backbone. Both are smooth Swish-family; SqrSwish is faster on FP16 hardware. Worth ablating against GELU on training stability + held-out PSNR/LPIPS. The implementation is 5 lines of PyTorch:

```python
class SqrSwish(nn.Module):
    def forward(self, x: torch.Tensor) -> torch.Tensor:
        return 0.5 * x * (1.0 + x / torch.sqrt(x * x + 1.0))
```

Independent reimplementation under Apache 2.0; the FSR 4 source defines it but the function is conceptually trivial and not novel-enough to warrant attribution beyond a pointer in the docstring.

## FasterNet block — already-public technique, validated by FSR 4

FasterNet (Chen et al., "Run, Don't Walk: Chasing Higher FLOPS for Faster Neural Networks", CVPR 2023) is a well-known efficient backbone. The block pattern:

```
input → Concat(input, skip) → Conv3×3 (PW) → Conv1×1 (with bias) → Activation → Conv1×1 → Add(residual) → output
```

**FSR 4's variant (48-feature, no-group):**

```hlsl
template<uint numFeatures>
void FasterNet48_NoGroup(...) {
    // Concat (channels), then 3×3 PW, then 1×1, SqrSwish, 1×1, Add
}
```

Works with `numFeatures=48`, hardcoded path. Edge handling uses "skip-invalid" padding (faster than zero-pad or border-replicate). AMD comment in the source:

> "Edge padding - instead of pad with zeros we pad with the border pixel values. It turns out that the lack of edge padding does not seem to be visible in games but improves performance a lot (especially in layers with big number of features like bottlenecks)"

**v6.2 borrowing:** Use FasterNet block as the body of the student backbone. Public technique, no attribution beyond paper citation needed. Implementation is straightforward in PyTorch (`nn.Conv2d` + `Concat` + activation + skip). The "skip-invalid edge padding" is a performance trick worth implementing in our CUDA kernel (not the PyTorch reference, where edge handling is autograd-determined).

Sketch:

```python
class FasterNetBlock(nn.Module):
    def __init__(self, channels: int = 48, hidden: int = 16):
        super().__init__()
        self.conv_pw = nn.Conv2d(channels, hidden, kernel_size=3, padding=1)
        self.conv_1 = nn.Conv2d(hidden, hidden * 4, kernel_size=1, bias=True)
        self.act = SqrSwish()
        self.conv_2 = nn.Conv2d(hidden * 4, channels, kernel_size=1)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        h = self.conv_pw(x)
        h = self.conv_2(self.act(self.conv_1(h)))
        return x + h
```

Independent reimplementation; FSR 4 uses HLSL with explicit register packing. Pattern is the same.

## Fused mega-kernels — the philosophy, not the ports

FSR 4 ships pre-fused HLSL kernels combining 4-7 operations:

| Fused kernel | Ops combined |
|---|---|
| `FusedConv2D_k1b_SqrSwish` | Conv1×1 + SqrSwish |
| `FusedConv2D_k1b_Relu` | Conv1×1 + ReLU |
| `FusedConv2D_k3p1b_Conv2D_k1b_SqrSwish_Conv2D_k1b_Add_Add` | Conv3×3 + Conv1×1 + SqrSwish + Conv1×1 + Add + Add |
| `FusedConv2D_k3p1b_Conv2D_k1b_SqrSwish_Conv2D_k1b_Add_Add_CT2D` | Same plus 2× upsample |
| `FasterNet.hlsli` | Whole FasterNet block |

**Why fuse:** each unfused operator pair has a write+read of intermediate FP16 tensors to global memory. Fusing means the intermediate stays in registers, saving roughly 2N reads+writes per fused-pair where N is the spatial size. On HR output (4K = 8M pixels), even at FP16 (2 bytes/channel), that's gigabytes of bandwidth saved per frame.

**v6.2 takeaway — design our own fused kernels:**

Don't port FSR 4's specific HLSL kernels. Instead, identify equivalent mega-fusion opportunities in our canvas-residual pipeline:

1. **Sparse R=8 splat → low-rank decode → composite** — fuse the R-channel rasterizer output with the 1×1 decoder + tonemap into a single CUDA kernel. Saves intermediate HR×R buffer write.
2. **Validity mask → reproject base → canvas warp → splat** — fuse the early-frame setup ops since they all consume the same MV/depth inputs. Saves multiple passes over the LR buffers.
3. **Backward gradient: accumulate in shared mem → one block→global atomic** — already in our v6.2 spec (TBDR backward). FSR 4 doesn't need backward (inference-only DLL); our pattern is canvas-side specific.

The fusion philosophy transfers; the specific kernels do not. Our pipeline is canvas+spawner+raster, not pure feedforward conv.

## INT8 weights + FP16 NHWC + DequantizeLinear

Production quantization recipe in FSR 4:

- Weights stored as INT8 in the binary
- Activations are FP16 throughout
- `DequantizeLinear.hlsli` decodes INT8 → FP16 with per-tensor scale + zero-point
- Tensors are NHWC (channels-last) layout — adjacent threads access adjacent channels for the same pixel; this matches the workgroup pattern of compute shaders

**v6.2 takeaway:**

For the **mid-high tier** (3080 Ti / 4070 mobile reference): use FP16 NHWC for activations + INT8 PTQ on the student weights. TensorRT supports INT8 PTQ with per-tensor calibration; this matches FSR 4's recipe and is the right starting point.

For the **mainstream tier** (4060/3060/RX 7600): same recipe; INT8 + FP16 keeps the model small enough for VRAM budget.

For the **entry ML tier**: drop to FP16-only weights (no INT8); dequant overhead may exceed gain on cards with limited INT8 throughput.

For the **no-ML shader tier**: not applicable; the rasterizer + LUT are FP16 with no learned weights.

**Implementation:** `oss/sr/v6/student/quantization.py` — TRT INT8 calibration on a representative training-corpus subset. Calibration set ~1000 frames from TartanAir oldtown + UE5 captures.

## Edge padding skip — small but effective

FSR 4's source comment is gold:

> "the lack of edge padding does not seem to be visible in games but improves performance a lot ( especially in layers with big number of features like bottlenecks)"

This is AMD's grad-student doing a real-world ablation and finding that the "obvious-correct" zero-padding is unnecessary for game content. Worth replicating in OSS:

- Our v6.2 student backbone can skip zero-pad on convs at the LR boundary
- Cost savings scale with channel count — most savings at the bottleneck (deepest features)
- Visual impact: in our held-out eval, compare student-with-pad vs student-without-pad → if no regression, ship without

Concrete: PyTorch `nn.Conv2d(padding=0)` + handle the boundary in CUDA inference kernel (skip-thread-if-out-of-bounds, no zero-fill). Training can still use `padding=1` with reflection or zero-pad if it converges better; the inference kernel is what matters for ms/frame.

## What we explicitly DO NOT borrow

1. **FSR 4's overall topology.** Whole-frame conv-stack ML upscaler IS the architecture class OSS is positioned to NOT be. Borrowing the topology = becoming another DLSS 4 / FSR 4 / XeSS competitor on their territory. Our differentiator is canvas-residual + structural FG.

2. **FSR 4's frame generation pipeline.** `ffx_provider_fsr3framegeneration_*.cpp` ships frame-gen as a separate signed binary. Our canvas warp = free FG. Adopting their FG approach throws away the structural advantage.

3. **`amdxc64.dll` driver dependencies.** FSR 4 binary requires AMD driver components for the matrix engines. We can't ship that; we run on the binary as-is for benchmarking purposes only.

4. **AMD-specific RDNA 4 INT8 matrix engine intrinsics in HLSL.** When we eventually ship our own AMD HIP path, we'll write our own kernels using ROCm intrinsics — not port FSR 4's HLSL.

## How this informs v6.2-pico-002 specifically

| Component | FSR 4 contribution |
|---|---|
| Student backbone (Tier 3a in priority stack) | FasterNet blocks + SqrSwish + FP16 NHWC + INT8 PTQ |
| Concat-fusion module replacing global cross-attn (Tier 2a) | Pattern of "concat input + skip → small MLP" matches our intended fusion architecture |
| Quantization recipe | INT8 weights / FP16 activations / per-tensor DequantizeLinear |
| Loss recipe | TBD; FSR 4 doesn't expose training source. We continue with L1 + LPIPS + distillation |
| Disocclusion handling | FSR 4 has no canvas; OSS-specific design (no FSR 4 contribution) |
| DGP dictionary covariance | Council convergence (ContinuousSR + 3-way model agreement); no FSR 4 contribution |
| Conic row recurrence (H001) | Our novel; no FSR 4 contribution |
| Frame extrapolation | Our structural advantage; FSR 4 confirms by NOT having it (separate DLL) |

Net: FSR 4 informs the **student backbone choice** (FasterNet + SqrSwish + INT8 NHWC) and validates our **mega-kernel fusion philosophy**. The canvas-residual + structural-FG architecture remains OSS-specific, untouched by FSR 4 borrowing.
