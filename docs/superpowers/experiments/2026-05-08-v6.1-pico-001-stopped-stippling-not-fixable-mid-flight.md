# 2026-05-08 — v6.1-Pico-001 stopped early: stippling not fixable mid-flight

## Status

v6.1-Pico-001 (training start 2026-05-07 12:00) is being stopped early at ~step 12k after the user reported the λ=2px stippling artifact has gotten visibly worse, not better, despite the in-flight `spawn_subpixel_jitter` change introduced in commit `221a325` (2026-05-08 10:53). Companion stippling-detection memo: `2026-05-08-v6.1-stippling-artifact-detection.md`. Architecture-audit memo: `2026-05-08-v6.1-stippling-artifact-architecture-audit.md`.

## Question

Did any of the in-flight stippling "fixes" actually affect the artifact, and what is the right next step — keep training or restart from scratch?

## Method

Static analysis of:
1. The actual code change in commit `221a325` (the only stippling-targeted change committed during pico-001's lifetime).
2. The argparse default for the new flag.
3. The mathematical structure of the introduced jitter vs the artifact's spatial frequency.
4. The user's empirical observation of artifact progression.

No FFT re-measurement at later steps was needed because the analytical case was conclusive on the code alone.

## Inputs

- Commit: `221a325` "v6.1(audit): root-cause stippling artifact + propose architectural fix"
- Files changed: `oss/sr/v6/model.py` (25 lines), `scripts/sr_train_v6.py` (9 lines), 2 test files, 1 audit memo
- Spawner code: `oss/sr/v6/gaussian_spawner.py` (no changes in this commit; the spawner itself was not touched)
- FFT residual peak (step 11000, prior memo): λx=2px @ 177,265, λy=2px @ 138,551
- Operator empirical observation (2026-05-08 ~14:00): "stippled look has only gotten worse"

## Output

### What `221a325` actually did

Added a config flag and a small jitter term in `model.py`:

```python
# Config:
spawn_subpixel_jitter: bool = False   # default OFF

# Spawner-offset compute (training only):
offset = torch.zeros((b, 2), device=device, dtype=torch.float32)
if spawn_offset_random:
    offset = offset + torch.randint(0, tile_size_hr, (b, 2)).float()
if spawn_subpixel_jitter:
    offset = offset + torch.rand((b, 2))   # ← the new bit
self._spawn_offset_xy = offset
```

### Critical finding 1: flag default is `False`

`scripts/sr_train_v6.py` line 192-194:

```python
p.add_argument("--spawn-subpixel-jitter", action=argparse.BooleanOptionalAction,
               default=False,
               help="Add continuous [0,1) HR-pixel spawner jitter during training. ")
```

Pico-001 has not been confirmed launched with `--spawn-subpixel-jitter`; the default-off behavior means unless the run was explicitly relaunched after `221a325`, the jitter has never been on for it.

### Critical finding 2: even if ON, the math is wrong

The jitter is `torch.rand((b, 2))` — one (x, y) pair **per batch element (per frame)**, NOT per Gaussian. All Gaussians in a frame share the same offset.

This shifts the **whole tile-grid origin** uniformly. It does not break the **sub-tile spatial relationships** between adjacent Gaussian centers within a tile.

The λ=2px checkerboard is a *sub-tile* phenomenon: the 2-pixel period is between adjacent Gaussians at consecutive integer pixel positions inside a single tile. Translating the entire tile grid by a uniform sub-pixel offset moves the checkerboard pattern in lockstep — it does not destroy the periodic structure.

### Critical finding 3: this is the WRONG-PERIOD fix from v6.0

The v6 → v6.1 transition introduced `spawn_offset_random` (random tile-grid origin per frame) plus rasterizer overlap with cosine feathering — that combination correctly addressed the **16-pixel grid artifact** (period = tile size). The new "subpixel jitter" is a continuous-valued variant of the same per-frame tile-origin trick.

Both target *tile-period* artifacts. The current artifact is *sub-tile-period* (λ=2). A uniform per-frame offset that successfully scrambles 16-pixel patterns can leave 2-pixel patterns completely untouched.

### Critical finding 4: per the user, the artifact is worsening

The model has trained ~30 hours with weights that produce the bias. Continuing to train without a structural fix means the loss landscape is locking in the failure mode — the optimizer is finding the local minimum that *includes* the checkerboard, because nothing in the gradient pressures it away.

### Combined assessment

- No effective stippling fix has actually trained on this checkpoint.
- Even the stand-by fix (the introduced jitter) targets the wrong spatial period.
- Continuing to train pico-001 cannot recover the artifact; the model has learned around it.
- The right action is to restart from scratch with a structural fix.

## Decision

Stop v6.1-Pico-001 now. Start v6.2-Pico-002 with the v4 architecture spec (`docs/architecture/2026-05-08-v62-arch-v4-spec.md`). The stippling-relevant pieces of v6.2:

1. **Disocclusion-pixel-center spawn**: spawn at exact disoccluded HR-pixel centers; let the canvas warp + motion-vector advection move Gaussians off-grid naturally over time. Decouples spawn-time grid alignment from sub-pixel positioning. (Gemini council fix.)
2. **DGP dictionary covariance**: replace direct (Δscale, Δrot) regression with a softmax over M=8-16 prototype Σ matrices fit from natural-image statistics. Forbids the integer-pixel-aligned local minimum by construction. (ContinuousSR + 3-way council convergence.)
3. **Per-Gaussian sub-pixel offset** (not per-batch): if jitter is added at all, it must be `torch.rand((G, 2))` — one offset per Gaussian, not per frame. Decoupling adjacent-Gaussian positions is what kills the 2-pixel period.
4. **R=4 latent splat + concat-fusion + counting-sort tile bin** (orthogonal to stippling but part of v6.2 commitment) — these compose with #1-3 multiplicatively and don't conflict.
