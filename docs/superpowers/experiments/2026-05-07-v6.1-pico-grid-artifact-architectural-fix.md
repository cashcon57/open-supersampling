## What was observed

Pico-001 (commit `f2c33a8` baseline; Net2Net code already landed but not active) was training cleanly post the bicubic-residual fix:
- Step-1 total loss: 12.22
- Step-20,320 total loss: 6.19
- 0 non-finite warnings, GAN warmup at step 20K kicked in cleanly

Visual viz strips (in-flight comparison: `LR | bicubic | v5-pixel | v6-pico | GT | |err v5| | |err v6|`) showed:
1. **Step 100**: v6 column close to bicubic (expected — bicubic-residual init).
2. **Step 5K-15K**: v6 column starting to diverge from bicubic with sharper edges, but a faint regular cross-hatched grid texture visible on smooth surfaces (walls, sky).
3. **Step 20K** (post-GAN warmup): grid pattern is **more visible**, not less. Approximately 16-pixel period, most prominent on smooth flat surfaces, present on detail-heavy regions but masked by texture.

User flagged it directly: "v6 finally looking different than bicubic, but has a waffle-ish kind of pattern to it."

## Hypothesis

Three components of v6 all operate on a 16-pixel grid:

| Component | Grid period | Source |
|---|---|---|
| HAT window-attention | 16 | `V6Config.window_size = 16` |
| `V6Rasterizer` tiles | 16 | `V6Config.tile_size_hr = 16` (gsplat-derived backend) |
| `GaussianSpawner` HR-space tile centers | 16 | `tile_size_hr` in spawner forward |

When all three align at the same period:
- HAT window boundaries always at 16-pixel offsets
- Rasterizer tile boundaries always at the same offsets
- Spawned Gaussian centers always at the same offsets

Residual misalignment at any one of those boundaries is small, but stacking three correlated 16-pixel-period structures compounds the artifact into a visible grid pattern.

HAT uses *shifted* windows internally (standard SwinTransformer pattern), which partially breaks the regularity. Rasterizer + spawner do not — they use fixed grid alignment for every frame, every training step.

## Why training is making it worse, not better

Initial expectation: training would smooth the grid via GAN-D + LPIPS pressure on tile boundaries.

Actual behavior: pattern becoming more pronounced over checkpoints. Mechanism:

- The grid is spatially correlated with EVERY input (every tile boundary aligns at the same pixels in every frame). The model sees this correlation in 100% of training samples.
- GAN loss + LPIPS at step 20K+ push the model toward producing *sharper* outputs.
- Sharper output + grid-aligned spatial correlation → the model learns to produce *sharper grid-aligned features*, not grid-free features.
- Continued training would converge to a higher-quality but more grid-aligned image, not a grid-free image.

This is a **structural failure mode**, not a training-time hyperparameter issue.

| Path | Wallclock to a clean shippable Pico | Notes |
|---|---|---|
| Finish Pico-001 (~9 more days) → retrain with fixes (~10 days) | ~20 days | The current run would converge with structural artifacts; would have to retrain regardless. |

Stopping now is faster *and* the v6 architecture lineage starts clean for Standard (Net2Net) and Heavy (cloud-trained). Without these fixes, every tier inherits the same grid artifact at v6-Heavy scale.

Decision: stop Pico-001, implement fixes, restart as v6.1-Pico-001 on the fixed architecture.

## The two architectural fixes

### Fix 1: Randomized spawner tile offsets per training frame

`oss/sr/v6/gaussian_spawner.py` currently centers spawned Gaussians at fixed HR pixel coordinates `(tile_x * tile_size_hr + tile_size_hr/2, tile_y * tile_size_hr + tile_size_hr/2)`. Modify to add a per-frame random integer offset `(dx, dy)` where each component is uniform in `[0, tile_size_hr)`:

  Spawned position = (tile_x * tile_size_hr + tile_size_hr/2 + dx,
                      tile_y * tile_size_hr + tile_size_hr/2 + dy)

The offset is sampled fresh per training frame (NOT per training step — same offset for all frames in a trajectory, so canvas continuity holds). At inference time, default offset = 0 (or a fixed scene-dependent offset). Cost: one extra random pair per frame, ~zero compute.

This teaches the model that the grid is not a real spatial structure. The model must learn features that work regardless of which 16-pixel offset the spawner uses.

### Fix 2: Overlapping rasterizer tiles with feathered weights

`oss/sr/v6/rasterizer.py` (and its underlying gsplat-derived backend) currently uses non-overlapping `tile_size_hr=16` tiles. Modify to use overlapping tiles with edge-feathered weights:

- Each rasterizer tile is `tile_size_hr` ON ITS BOUNDARY but composites a `tile_size_hr + 2*overlap` (e.g. 16 + 8 = 24) region.
- The pixels in the overlap region are weighted by a smooth feathering function (cosine, gaussian, or simple linear ramp) so contributions from adjacent tiles blend continuously rather than seam-cut.
- Standard pattern in tile-based renderers (gsplat does this in its production HR path).

Cost: ~1.3-1.5× rasterizer compute. Since rasterizer is currently <30% of v6's per-step time, this lifts v6 step time by ~10%. Acceptable.

This eliminates rasterizer tile seams *by construction*, independent of how well-aligned the spawner / window-attention boundaries happen to be.

### Why both fixes together

- Fix 1 alone: spawner randomization makes spawning grid-agnostic, but rasterizer + HAT-window seams still align in 50% of frames (when offset = 0 mod alignment).
- Fix 2 alone: rasterizer feathering eliminates the rasterizer's contribution to the grid, but spawner + HAT seams still produce a residual grid in features.
- Both together: every component is either offset-randomized or seam-feathered. Grid period is no longer a structural feature anywhere in the chain.

## Open questions (revisit after v6.1-Pico-001 step-100K)

- Does the random spawner offset need to apply at inference too, or default-zero is fine? Probably depends on whether the inference frame's content correlates with offset = 0 specifically.
- Is `2 * overlap = 8` the right overlap, or should we go wider (16) for better blending at the cost of more compute?
- Does the GAN discriminator need any modification? Likely no — it operates on full HR images, not tiles.
